# The pictures: what makes them, and why they are committed

Every image in this repository is generated by a script and checked in.
This document says which script makes which picture, how to regenerate
them, and why they are artifacts rather than test assertions — which is a
deliberate decision and the one thing here worth arguing about.

## Why these are artifacts and not assertions

Every renderer in this project already has tests, and they assert what the
drawing *claims*: that the zero level set sits on the outline, that a
clearance ring sits at the clearance, that a part lands where the layout
put it. Those state invariants, so they fail when the code is wrong and
pass when it is merely different.

What they cannot notice is a change that keeps every invariant and still
looks wrong — a fade constant that washes the field out, a stroke weight
that makes the cell grid compete with the objects, a click marker that
comes out four pixels wide.

A stored-image assertion is the obvious fix and the wrong one here.
**Eleven of this project's test modules sit downstream of a stochastic
search**, so any change to the solver reddens them all at once, and the
only possible response is to re-bless the lot — which teaches nothing and
trains the reflex that lets a genuinely bad change through next time.
Measured on this repository the day the spacing pass was corrected: every
part moved, legitimately, and three test modules' worth of images would
have needed regenerating without a soul looking at one.

So the pictures are committed and regenerated by hand. A visual change
arrives as a diff somebody reads, not as a red build somebody silences.
The tests that do exist around them check that the *machinery* works — a
frame is not sheared, a beat is not blank, a gallery entry actually writes
a file — never that a picture looks like a stored copy of itself.

## What makes what

| Script | Writes | Cost | Needs |
| --- | --- | --- | --- |
| `capture_demo.py` | `capture.gif` | ~10 s | Qt, a cached SAM2 checkpoint |
| `layout_demo.py` | `pack.gif`, `group.gif`, `drawer.gif` | 15 s / 2.5 min / 30 s | — |
| `screenshot_demo.py` | `window_*.png` | ~2 min | Qt |
| `solid_demo.py` | `solid_*.png` | ~30 s | OpenSCAD, the submodule |
| `render_demo.py` | `preview_*.png` | ~5 s | — |
| `generate_aruco_sheet.py` | `sheet_aruco.png` | ~2 s | — |

All of it lands in `docs/media/`. The Makefile targets are `gifs`
(`gif-capture`, `gif-pack`, `gif-group`, `gif-drawer`), `screenshots`,
`solids`, `previews` and `sheet` — none of them part of `make check`, for
the reason above.

`make -j4 gifs` runs the animations at once; nothing in the layout package
is threaded, so on a spare machine that is close to a 4× saving.

### The animation commands, and what their flags are for

These are what the `gif-*` targets run. Keep the two in step.

```
capture_demo.py --out docs/media/capture.gif

layout_demo.py pack \
    test_data/small_spoon.svg test_data/medium_spoon.svg test_data/big_spoon.svg \
    test_data/medium_fork.svg --out docs/media/pack.gif \
    --restarts 8 --every 8 --pixels-per-mm 1.4 --colors 8

layout_demo.py group \
    test_data/big_spoon.svg test_data/small_spoon.svg test_data/screwdriver.svg \
    test_data/spreader.svg test_data/big_measure.svg test_data/small_measure.svg \
    --start one-per-bin --restarts 12 --every 1 \
    --out docs/media/group.gif

layout_demo.py drawer \
    test_data/small_spoon.svg test_data/medium_spoon.svg test_data/big_spoon.svg \
    test_data/small_fork.svg test_data/medium_fork.svg test_data/big_fork.svg \
    test_data/spreader.svg test_data/screwdriver.svg \
    test_data/small_measure.svg test_data/big_measure.svg \
    --drawer 210x340 --drawer 170x130 --restarts 6 --every 1 \
    --out docs/media/drawer.gif
```

`--every` is how many search steps go into one frame, `--restarts` is how
hard the search looks, and `--pixels-per-mm` and `--colors` trade file
size against legibility. `--drawer` is a drawer's interior in millimetres
(or `11x9 cells`) and can be repeated.

`--start one-per-bin` gives the grouping search the most to find, which
makes for a better animation than the state it actually starts from;
`--start first-fit` is what `Group` does, and reaches the same 25 cells
here.

## Recordings of real windows

The capture animation and the three window screenshots are `QWidget.grab()`
of an actual running window, driven offscreen with
`QT_QPA_PLATFORM=offscreen`. Nothing is mocked up and no panel is drawn by
hand.

That distinction earns its cost. A picture of the packer is a picture of
an algorithm, and rendering it directly is honest. A picture of a *window*
is a picture of an interface, and one assembled out of separately-rendered
panels would be a mock-up — it would keep looking right after the real
window had stopped working. It would also be missing the half that cannot
be reconstructed from the pipeline at all: the sizes, the status lines,
the units, the buttons somebody has to find.

The shared machinery is `pipeline/window_capture.py`, and it exists
because three separate things each produced a plausible-looking wrong
picture:

- **Qt pads scanlines** to a 4-byte boundary. Reading the buffer as
  `width * 4` shears the image progressively down the frame on any odd
  width, which reads as a rendering bug rather than an indexing one.
- **`QImage.bits()` returns memory Qt reuses.** A frame that aliased it
  showed whatever the window looked like last, in every frame at once.
- **Qt lays out lazily.** A grab taken without settling shows the state
  *before* the change that prompted it, so the whole animation runs one
  beat behind itself. `Settled` loops until two consecutive grabs agree,
  rather than pumping a fixed number of passes, because how many rounds a
  panel needs is a property of the widgets and a tuned constant would
  quietly stop being enough when somebody added to them.

### The capture animation

`capture_demo.py` records six beats: empty window, photo loaded and
calibrated, the two click points, the segmented outline, lateral symmetry
ticked, the contour selected and rectified. Frame-to-frame differences on
the committed recording:

```
0->1: 325492 px   photo + calibration
1->2:    241 px   two click markers
2->3:   2356 px   segmented, yellow outline
3->4:    752 px   lateral symmetry ticked
4->5:  28156 px   selected, green fill + millimetres
```

Two constraints shape it. It **must use a photo with a calibration sheet
in frame** (`test_data/screwdriver.jpg`), because without one the window
falls back to pixel space by design and the animation would look complete
while dropping the one thing it exists to show. And it **drives real
widgets rather than setting the parameters behind them** — the symmetry
beat ticks the actual checkbox, because an outline that reshaped itself
next to an unticked box would read as the tool acting on its own.

The palette is 128 colours rather than the layout animations' 16. Those
are line drawings on white, where 16 is generous; this is a photograph,
and at 16 it came out uniformly brown with the ArUco markers illegible —
which would make it evidence for nothing, since whether the markers are
readable is the question calibration answers.

### The window screenshots

`screenshot_demo.py` drives each window through the same methods a
person's clicks reach: load these files, type this drawer size, press
Plan, wait. The floorplan picture runs a real search with a reduced
restart budget (8 rather than 24 — measured to reach the same 25-cell
grouping on that library), which is why it is the slow one.

Window sizes are set by the *panel*, not by the picture. These windows
report a size hint that ignores their word-wrapped status labels, so at
800 px tall the line saying what the search found was cut off half way
through — a screenshot advertising a status the window could not show.

## Renders of the actual bin

`solid_demo.py` packs real contours, writes the same `.scad`
`layout_cli.py` writes, and hands it to OpenSCAD. The picture at the top
of the README is therefore the solid somebody would slice, pockets and
stacking lip and all.

CGAL (`--render`) rather than the fast preview: the preview renderer draws
subtracted volumes with their surfaces fighting, and a picture of a bin
whose pocket flickers is worse than no picture. `--viewall --autocenter`
rather than a fixed camera, since the bins differ in size by a factor of
three; the flat background OpenSCAD leaves is then cropped off, which is
framing rather than retouching.

The `.scad` it feeds OpenSCAD is a temporary file rather than a committed
artifact. `solid.GenerateScad` writes the library include as an absolute
path - deliberately, so the program renders from any directory - which
makes it specific to whichever machine generated it, and committing it
would produce a diff on every checkout that regenerated the picture.

## The still renderings

`render_demo.py` photographs the *renderers*, one picture per drawing
path, and everything it draws is deterministic: hand-written placements,
fixtures loaded from files, and the drawer assignment, which is exhaustive
and carries no RNG. Nothing there calls the stochastic solver, or the
pictures would change on their own and the diffs would mean nothing.

That is the difference between these and the screenshots. A preview is a
reference image whose job is to make an unintended visual change visible;
a screenshot is documentation whose job is to show a person what the tool
looks like. The first has to be reproducible to the pixel. The second only
has to be true.

## When to regenerate

The animations are phony targets rather than dependency-tracked ones, on
purpose: what they actually depend on is the behaviour of the whole layout
package, and a prerequisite list broad enough to be correct would
regenerate them — at several minutes — every time a test file was touched.

So they go stale silently. Regenerate whenever a change moves parts
around, changes what a window shows, or changes what a bin looks like.
`Distribute` has now done the first of those twice.
